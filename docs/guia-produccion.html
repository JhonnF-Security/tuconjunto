📦 Módulo 0 — Arrancar y comprobar vida 3 pasos

Antes de probar cualquier lógica, confirma que el proceso vive. Todo backend serio expone /api/health: responde sin tocar la BD. Es tu primer latido.

¿Por qué un endpoint de health separado?

Diferencia vivo vs sano: health solo prueba "el proceso corre". No consulta la BD a propósito — así distingues "el server murió" de "la BD tiene problemas" en segundos. Los balanceadores y monitores usan este patrón (liveness probe).

Concepto · Cookie HttpOnly y anti-CSRF

HttpOnly: el JavaScript del navegador no puede leer la cookie → aunque hubiera un XSS, no roba la sesión. X-Requested-With: fetch es el anti-CSRF: un sitio malicioso externo puede disparar formularios hacia tu API, pero no puede añadir cabeceras personalizadas → sus peticiones reciben 403 CSRF. Dos capas independientes.

Concepto · RBAC vs IDOR (los dos enemigos distintos)

RBAC pregunta "¿puede este ROL hacer esta acción?" → requireRole('administrador').

IDOR pregunta "¿este recurso es SUYO?". Ejemplo real en reservas.js:

if (reserva.usuario_id !== req.usuario.id)
  throw httpError(403, 'SIN_PERMISO', 'Solo quien creó...');

Sin esa línea, cualquiera cambiando /reservas/7/cancelar cancelaría reservas ajenas. Regla: rol controla el tipo de acción; ownership controla sobre qué fila. Recursos personales necesitan ambos.

🔐 Módulo 2 — Seguridad: los 4 fixes y su lógica OWASP

Cuatro vulnerabilidades reales encontradas por auditoría, corregidas y verificadas en vivo. Cada una enseña un principio distinto.

requireAuth línea por línea
① token = leerCookie(req,'tc_session')        // el navegador lo adjunta solo
② fila = SELECT ... WHERE token_hash = sha256(token)   // ¡hash, no token plano!
③ if (!fila) → 401                            // token desconocido
④ limpiarSesionesExpiradas(...)               // higiene de la tabla
⑤ if (expirada) → 401 SESION_EXPIRADA
⑥ if (estado!=='Activo') → borrar sesiones + 403   // ← nuestro fix A-1
⑦ req.usuario = perfilUsuario(fila)           // todos los routers confían en esto
⑧ if (debe_cambiar_clave && !url.startsWith('/api/auth')) → 403
⑨ next()                                      // continúa al router

② es oro puro: la BD guarda SHA-256 del token. Si te roban la BD completa, esos hashes NO sirven para suplantar a nadie (necesitarías preimágenes). Lección: nunca guardes credenciales reversibles.

Concepto · Math.random() vs crypto.randomBytes

Math.random() es un PRNG predecible: observando suficientes salidas se reconstruye su estado interno y se predicen las siguientes. crypto.randomBytes() usa el CSPRNG del kernel (entropía real). Para claves/contraseñas/sesiones: SIEMPRE crypto. 48 bits ≈ 281 billones de combinaciones; con rate-limit de 5 intentos/min la fuerza bruta online es inviable.

Concepto · scrypt y comparación en tiempo constante

{N:16384, r:8, p:1} ≈ 16 MB de RAM por hash. scrypt es memory-hard: limita a los atacantes con GPU (que son malas con RAM). OWASP lo recomienda como mínimo actual.

crypto.timingSafeEqual(a,b) compara byte a byte SIN cortocircuito. Un === entre strings aborta en el primer byte distinto → el tiempo revela cuántos bytes acertaste.

Formato almacenado scrypt$salt$hash con salt aleatorio de 16 B por usuario → misma contraseña produce hashes distintos → tablas precalculadas (rainbow tables) inútiles.

Pendientes menores documentados (no bloqueantes)

· Enumeración vía mensajes de login (429 vs 401 distintos) — mitigable con respuesta uniforme.
· XSS almacenado en campos libres: mitigado por CSP con nonce; conviene sanitizar server-side.
· Rate-limits en memoria: se reinician al reiniciar el proceso; para multi-instancia usar Redis.
· CSP podría añadir object-src/base-uri/frame-ancestors.

🚀 Módulo 3 — Los 5 bloqueantes de despliegue VPS corregidos

Errores que SOLO aparecen el día del despliegue real, no en tu máquina. Cada uno con su lección.

Anatomía de X-Forwarded-For (por qué exactamente 1 salto)

nginx CONCATENA lo que envió el cliente, no lo reemplaza:

X-Forwarded-For: basura_falsa_del_cliente, IP_real
                  ↑ NO confiable            ↑ último salto confiable

TRUST_PROXY=1 = "cuenta 1 salto desde atrás": toma la IP que TU nginx puso, ignora la basura del cliente.

· TRUST_PROXY=0 → todos comparten bucket (DoS accidental)
· TRUST_PROXY muy alto → el atacante rota su XFF falso y evada límites
· Exactamente los saltos que TÚ controlas = precisión sin exposición.

Bonus · Hardening systemd traducido a humano

· ProtectSystem=strict → filesystem completo solo-lectura, excepto…
· ReadWritePaths=data backups → …estas dos carpetas
· NoNewPrivileges=true → jamás puede escalar a root (bloquea setuid/sudo)
· PrivateTmp=true → /tmp propio invisible para otros procesos
· CapabilityBoundingSet= (vacío) → sin capacidades mínimas de root
· MemoryMax=768M → techo de RAM para GC de V8

⚠ NUNCA MemoryDenyWriteExecute=true con Node: prohíbe memoria escribible+ejecutable y el JIT de V8 necesita exactamente eso → el server moriría al arrancar.

Además el arranque hace process.umask(0o077) → la BD nace 600 (solo dueño lee): aunque comprometan otro servicio del VPS, no lee PII.

🌍 Módulo 4 — Desplegar en tu VPS, paso a paso producción

Requisitos: VPS Ubuntu 22.04/24.04 (1 vCPU/2 GB/40 GB basta para decenas de conjuntos), dominio propio, puertos 22/80/443.

Operación diaria (chuleta)
systemctl status tuconjunto        # estado
systemctl restart tuconjunto       # reiniciar
journalctl -u tuconjunto -f        # logs en vivo
sudo -u tuconjunto npm run backup  # backup manual

# Restaurar backup (¡procedimiento seguro!):
systemctl stop tuconjunto
cp backups/tuconjunto-FECHA.db data/tuconjunto.db
rm -f data/tuconjunto.db-wal data/tuconjunto.db-shm   # ¡OBLIGATORIO!
sqlite3 data/tuconjunto.db "PRAGMA integrity_check;"   # debe decir "ok"
chown tuconjunto:tuconjunto data/tuconjunto.db*
systemctl start tuconjunto

¿Por qué borrar -wal/-shm? SQLite en modo WAL escribe en archivos auxiliares constantemente; restaurar el .db sobre -wal viejos = mezclar dos estados = corrupción.

¿Por qué backup con VACUUM INTO? Saca foto consistente MIENTRAS el server sigue corriendo. Copiar el .db a medias bajo WAL = corrupción garantizada tarde o temprano.

Actualizar la app más adelante
rsync -av --exclude node_modules --exclude data --exclude backups \
  --exclude tls --exclude .env ./ root@VPS:/opt/tuconjunto/
ssh root@VPS systemctl restart tuconjunto

El esquema es idempotente al arranque: las nuevas tablas se crean solas, los datos existentes no se tocan.

Escala futura (>50 conjuntos)

· SQLite → PostgreSQL (solo cambia db.js; el contrato API no cambia)
· Notificaciones email/WhatsApp a un worker aparte
· Backups offsite: rclone copy backups/ b2:tuconjunto-backups
· Costos: VPS US$5–12/mes · dominio US$10–15/año · TLS gratis · PSE real ~2,5–3,5 % por transacción

💳 Módulo 5 — Pagos PSE reales con Wompi F0→F5

Hoy existe un simulador interno (POST /api/pagos/pse). Está diseñado para enlazarse a una pasarela real sin cambiar el modelo de cuotas. En producción real, el simulador debe desactivarse — hoy cualquiera podría autocompletarse una cuota gratis con curl.

Lo que YA cumple el proyecto (reutilizable tal cual)

✅ Monto SIEMPRE desde la BD (el cliente nunca envía valor)
✅ Idempotencia: transacción SQLite atómica + UNIQUE(unidad_id,periodo) → doble pago imposible (409)
✅ Referencia visible PG-XXXXX, auditoría, cartera y KPIs derivados del estado
✅ Infraestructura webhook-ready: TLS, rate-limiting, logs
